## 可直接使用的项目描述

> 开发“知源 · 个人 RAG 知识助手”，复用 DocsGPT 的上传、会话和引用，提供可自定义知识库及中英文固定使用指南；以 AI 开发文档和源码作为评测场景，接入并审计49,505个官方唯一语料ID，完成53题DEV和150题本地留出集的八种检索条件对照。预先选定普通Hybrid，在留出集将Coverage@10从49.06%提升至57.64%（+8.59个百分点，95%配对bootstrap区间[+3.16,+13.53]），α-nDCG@10提升0.0583；通过固定预算上下文诊断揭示排名收益并未稳定转化为装箱覆盖，保留标识符、现代重排、语境前缀等负结果及工程故障。固定30题生成/控制、两种复检的完整验证和最终交付仍在进行；人工评分0，不宣称回答准确率提升或任意上传文档获得相同收益。

## 面试时如何解释取舍

**为什么选混合检索？** 代码标识符和错误码具有精确词法特征，dense 提供语义补充。H1 相对 B0 的 DEV 排名结果支持继续验证，但 H1 相对普通 hybrid 的增量很小，不能把全部收益归因于标识符分词。统一预算后 H0 装箱覆盖 0.33014 高于 H1 的 0.31402。随后 DEV12 中 H0 完成 12/12 个格式与引用有效回答，含失败整体效用为 2.2333/3，高于其余三组，所以暂选 H0。小样本富集、历史接口失败和评分模型独立性限制都保留，不能写成总体正确率。

**为什么没有默认使用重排？** DEV中R1的Coverage@10/alpha-nDCG都下降，R2 coverage微升但alpha-nDCG下降，因此在TEST前没有选入默认流程。两种重排的TEST150仍完整运行，用于验证预先选择并保留负结果；不能根据已看到的TEST重排成绩重新选型。

**怎样保证评测公平？** 统一官方 ID、完整语料、共享实现、固定拆分和同一候选池，记录配置/模型/代码哈希；显式区分原生 U 的 45,000 token 候选截断与受控 B0。U 使用共享 Qwen，不能称原厂默认 Granite。

**参考答案是否一定正确？** 不一定。事后复查 DEV 题 77124499 时发现，参考答案可能把“合并所有文本”和“在同一索引保存独立带元数据的块”混为一谈，AI 评分据此把元数据过滤方案判错。冻结的 Pinecone 示例本身支持过滤检索，现行[官方文档](https://docs.pinecone.io/guides/search/filter-by-metadata)也支持这一点。但候选回答引用了 Chroma 示例，不能因此宣称其 Pinecone 代码和全部主张都已被证据支持。我们将参考合理性与引用支持分开复核，原标签、AI 分数和统计分母全部保留；目前只是 AI 分析发现的人工复核候选，不是已经完成的人类裁决。依据见 `reports/gold-reference-flag-dev-77124499.json`。

**门控是否提高准确率？** 当前没有建立这一结论。H0/Q/QAlways 的 53 题复检对照中，按需分解的装箱覆盖比 H0 增加 1.42 个百分点，但区间跨零。新的 H0/Q/G/Full DEV12 已完整生成并完成同题 AI 评价：含失败的整体效用分别为 1.967、1.233、0.917、1.033（满分 3）。G 相对 H0 为 −1.05，95% 配对 bootstrap 区间 [−1.733, −0.400]；G 有 7/12 次运行失败，不能将差值归因于纯门控算法，也不能把这些失败算有效拒答。Full 唯一的合法非回答被 AI 判为误拒答，人工尚未核验。四种方法的DEV10控制题已经完整结束；H0/G的TEST30控制对照仍未完成，不能提前填写留出控制比例。发生本地服务中断的旧批次保留为故障记录，各独立批次和不同评分协议不混算。依据为 `reports/dev-decision-ai-quality-v4/summary.json`。

**为什么实现了新方法却可能不默认启用？** 必做的是实现并公平验证三个检索方向及证据门控，收益是假设。历史 DEV12 和新的决策 DEV12 均以 H0 的含失败效用最高，但新方法同时增加了调用与故障面。完整 DEV 控制四组各10题结束后，正式选择 H0；留出检索仍覆盖八种本地条件及 Q/QAlways 各150题，不通过省掉负结果美化项目。首次锁已在 TEST 前冻结，五组本地各150题执行后，文档 U+2028 触发读取器的 JSONL 拆行错误。原结果保留，只修正解析、另开 v2 冻结与完整执行；选择和参数不变，完整 TEST 报告尚未完成。

**产品是否真的答过问题？** 当前 prompt v2 的原生 H0 回答已复验，答案文本与实际 pipeline 结果一致，两个引用打开的是保存的文档和 Python 源码快照。一次逻辑生成经历两次网络尝试，端到端 125.97 秒；回答仍错误地把 `text_content=False` 的理由解释为字段是字符串。工程链路成功不代表语义正确，错误保留于失败案例和 MVP 视频，不能用单例替代正式质量评估。旧 v1 smoke 与 gate 恢复 probe 的修复成本也单独保留。

**生成模型与上下文如何控制？** 当前授权网关路由的请求名与返回名不一致，底层模型身份未验证；所有方法统一使用 4,000 `cl100k_base_proxy_v1` 代理 tokens，采用校验 SHA256 的上游内置 tokenizer，并非未知生成模型的精确 tokens。旧 4,000 UTF-8 字节协议造成证据不足，已取代。H1 装箱覆盖从 0.15723 到 0.31402 是协议修正诊断，不能写成算法提升或回答准确率。

**最有价值的失败是什么？** 除重排负结果，四组 DEV12 生成共 48 次尝试中有 36 题进入格式/引用修复，说明输出合同可靠性也是产品瓶颈。H1 的成功子集 AI 均分最高，但只有 6/12 成功；若删掉失败样本就会选错方案。我们保留失败分母、修复费用和历史接口限制，不把成功子集均分当总体表现。每个故障都区分“代码修复”“smoke 成功”和“完整业务验收”。

**能举一个检索指标误导决策的例子吗？** DEV 题 77561864 问怎样将 PDF 接入 agent。H0、H1 的 top-10 nugget 覆盖均为 6/7，但固定预算装箱后分别剩 5/7 和 1/7：H1 把 PDF loader 放在首位，真正有关 agent 工具集成的块虽已召回却未装入。我们因此同时观察最终上下文覆盖和实际正相关文档占比，而不只看 top-10。全 DEV 的 C 覆盖更高、证据密度却低于 H1，说明优化存在取舍；回答收益仍待生成评测和人工验证。详见 [具体失败案例](FAILURES.md)。
